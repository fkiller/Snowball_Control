# 원격 접속·모바일·배포 확장 작업 명세

> 상태: 개발 중인 작업 명세. 이 문서의 요구사항과 완료 조건은 구현 또는 출시 완료를 의미하지 않는다. 현재 동작과 보안 경계의 기준은 [아키텍처](ARCHITECTURE.ko.md)와 [영문 원본](ARCHITECTURE.md)이다. 구현·검증 상태가 바뀌면 두 아키텍처 문서도 함께 갱신한다.

## 1. 목표와 사용자 경험

사용자가 자신의 PC에서 실행 중인 Snowball을 외부 브라우저와 모바일 앱에서 안전하게 사용한다. 원격 기능을 선택하지 않은 사용자의 로컬 웹, 하드웨어, 하네스 제어는 기존처럼 인터넷 및 클라우드 계정 없이 동작한다. PC의 전원·로그인·절전 상태는 원격 가용성에 영향을 주므로, 앱은 준비되지 않은 PC를 온라인으로 가장하지 않는다.

첫 사용은 PC에 Snowball을 설치·실행하고, PC에서 원격 연결을 명시적으로 켜며, 휴대폰 또는 브라우저를 안전하게 등록하는 흐름이다. 초기 사설 접속 후보는 Tailscale이다. 사용자는 양 기기의 설치·로그인과 네트워크 정책 설정이 필요할 수 있음을 미리 알아야 한다. 장기적으로 전용 중계·계정 서비스를 검토하되, 이를 로컬 제어의 필수 조건으로 만들지 않는다.

일반 사용자는 서명된 설치 파일이나 OS에 맞는 짧은 한 줄로 PC 앱을 설치하고, 설치 후에는 트레이 또는 `snowball update`처럼 짧은 명령으로 갱신할 수 있어야 한다. 플랫폼별 명령어가 다를 수 있으며 Node/npm의 사전 설치 여부는 안내에 명시한다. 모바일 앱은 스토어에서 받을 수 있지만 PC 측 설치와 등록이 필요하다.

## 2. 범위와 현재 출발점

- 기존 실행 계층과 하네스·디바이스 계약을 유지하고, 원격 요청만 별도의 인증·인가 경계에 둔다. 하네스의 실제 모델·세션·프로젝트 발견과 승인 정책은 계속 원천 시스템을 따른다.
- 원격 웹과 모바일은 공통의 버전 있는 원격 계약을 사용하되, 브라우저 세션과 네이티브 기기 인증의 위험을 각각 다룬다. 기존 LocalClient를 외부 주소로 바꾸거나 로컬 API 전체를 프록시하지 않는다.
- 현재 브랜치에는 기본 비활성·별도 루프백의 실험적 읽기 게이트웨이, 수동 입력 방식의 모바일 실험 앱, 소스 업데이트 단축 명령과 멀티 저장소 점검 도구가 있다. 실제 상태는 아키텍처 문서와 해당 코드로 확인한다.
- 현재 실험은 정식 기기 페어링, 신뢰할 수 있는 호스트 신원 증명, 제품용 TLS 접속, 원격 웹·명령 실행, 앱스토어 출시, 서명된 릴리스 또는 원자적 업데이트의 완료를 뜻하지 않는다. 이 문서의 이후 단계는 목표다.

**현재 진행 상태:** 로컬 트레이에서 실험 리스너와 8시간 읽기 자격을 관리하며, 비공개 저장소에 자격 해시를 유지한다. 이는 개인키 증명 기반 기기 등록이 아니다. 비정상 종료 뒤 남은 새 형식의 잠금은 소유자 종료를 확인한 경우에만 트레이에서 복구할 수 있으며, 구버전 잠금·남은 복구 가드·미확인 소유자는 거부한다. 이전 개발 전용 복구 API와 동시 사용은 지원하지 않는다. 사용자가 승인한 Tailscale 실행 파일로 PC의 로컬 상태를 확인하는 트레이 기능과 인증서·정확한 호스트를 명시한 개발용 TLS 게이트웨이가 추가됐다. 실제 Tailscale 설정이나 모바일과의 연결을 활성화하지 않으며, 모바일의 자격 전송은 게이트웨이 신원 검증 전까지 차단한다. 소스 업데이트 경로에는 브랜치 혼합 방지 검사가 추가됐고, 일부 Unix 환경에서는 이미 PATH에 있는 `~/.local/bin`에 명령을 연결한다. Node/npm이 설치된 경우 GitHub 기반 `npx` 한 줄로 일반 `main` 소스 설치기를 실행하는 선택지도 추가됐다. 별도 새 폴더에 6개 저장소의 고정 SHA를 설치하는 개발용 경로를 npm 실행기의 명시적인 `--manifest` 모드에서도 호출할 수 있다. 모바일 전송 함수 자체도 미검증 상태에서 무조건 거부하며, 개발 진단은 Serve 스냅샷을 읽기 전용으로 분류할 수 있다. 실제 양쪽 기기 연결은 아직 검증하지 않았다.

PC에는 비활성 소스 수준으로 전용 P-256 TLS 키·자체 서명 인증서를 OS 비공개 저장소에 생성·재사용하고 손상·만료·잘못된 호스트·권한 이상을 거부하는 구성요소가 추가됐다. 인증서 지문을 고정한 Node 테스트는 같은 호스트의 다른 인증서를 거부하지만, 모바일 네이티브 인증·기기 키 소유 증명·사용자 확인·인증서 교체·독립 검토는 구현 또는 인수 완료가 아니다. 이 구성요소는 트레이나 원격 리스너에 자동 연결되지 않는다.

## 3. 위협 모델과 불변 보안 경계

보호 대상에는 세션과 대화 내용, 워크스페이스 경로·파일, 하네스 자격증명, 명령·승인 권한, PC·휴대폰 기기 자격과 업데이트 경로가 포함된다. 세션 수와 하네스 종류만으로도 작업 정보가 노출될 수 있다.

검토할 공격자는 인터넷 및 같은 네트워크의 미인증 사용자, 다른 tailnet 기기나 도난된 휴대폰, 악성 웹사이트·잘못된 프록시, 변조된 설치·업데이트 공급망, 중간자, 유출된 토큰을 가진 사용자다. 사용자의 PC 계정이나 관리자 권한이 이미 완전히 장악된 경우까지 앱이 보장하는 것은 아니다. 해당 한계와 복구 방법을 설명한다.

1. **로컬 경계 유지:** 무인증 로컬 Supervisor는 `127.0.0.1` 전용이다. 외부 포트 바인딩, Host/Origin 재작성, 공개 터널이나 리버스 프록시를 통해 이 화면과 전체 API를 노출하지 않는다. 기존 MK20 UDP·개발 ADB를 WAN 전송 수단으로 사용하지 않는다.
2. **별도 원격 입구:** 명시적으로 활성화된 게이트웨이만 버전 관리된 허용 작업을 제공한다. 인증 실패나 권한·저장소 오류는 기본 거부한다. 파일 읽기·설정·플러그인·기기 설정을 기존 로컬 API에 있다는 이유로 자동 제공하지 않는다.
3. **전송과 인가 분리:** 원격 전송은 암호화하고 PC의 신원을 검증한다. Tailscale의 사설망·ACL은 전송 접근 제한에 활용하되, Snowball의 기기 식별·권한·철회 및 브라우저 방어를 대체하지 않는다. HTTPS 인증서 또는 `.ts.net` 주소만으로 그 PC가 사용자 소유임을 증명했다고 주장하지 않는다.
4. **최소 권한과 민감한 작업:** 우선 명시적으로 허용한 읽기 범위부터 제공한다. 프롬프트 전송, 중단, 도구 승인과 파일 접근은 실제 PC 권한으로 이어지므로 별도 범위와 사용자 확인 정책을 둔다. 네이티브 하네스 승인 여부를 대신 만들어내지 않는다.
5. **기기별 철회:** 사용자가 기기 이름·권한·등록 및 마지막 사용 정보를 확인하고 개별 철회할 수 있어야 한다. 철회는 활성 세션과 진행 중 스트림에도 적용하며, 유효 기간 만료·기기 분실·PC 교체·시계 변화·백업 복원의 동작을 정의하고 시험한다.
6. **브라우저 보안:** 원격 웹 세션은 별도 인증, 적절한 쿠키와 세션 수명, CSRF 및 Origin 검사, CSP와 콘텐츠 이스케이프를 적용한다. 토큰을 URL·로그·브라우저 영구 저장소에 흘리지 않는다. 기존 Supervisor의 Origin 검사는 원격 사용자 인증이 아니다.
7. **비밀과 기록:** 자격증명·대화 내용은 기본 로그, 충돌 보고, 알림 및 분석에 넣지 않는다. 인증 실패와 민감 작업의 감사 기록은 필요한 최소 정보·보존 기간·사용자 접근 경로를 정한다. 백업·내보내기에서 기기 비밀의 포함 여부를 명시한다.
8. **플러그인과 OS 권한:** 기존 자식 프로세스는 OS 수준 파일시스템 샌드박스가 아니다. 원격 등록·설치·파일 접근 권한을 자동 부여하지 않고, 필요한 격리와 실제 하네스 정책의 경계를 검증한다.

## 4. PC 등록 및 기기 페어링 요구사항

사용자가 PC의 신뢰할 수 있는 로컬 UI에서 등록을 시작한다. 초대는 짧은 유효 시간·일회 사용·사용자 취소를 지원하고, PC와 모바일이 같은 연결 대상임을 양쪽에서 확인할 수 있어야 한다. 기기별 키 생성·소유 증명과 호스트 신원 검증에는 검증된 표준과 라이브러리를 채택하고 프로토콜·위협 모델에 대한 독립 검토를 거친다. QR은 편리한 전달 수단이지 화면을 볼 수 있는 타인이나 중간자에 대한 자동 방어가 아니다. 장기간 사용할 bearer 비밀을 무검증 QR·URL·로그에 노출하지 않는다.

모바일 개인 키는 플랫폼 보안 저장소를 사용하고, 비내보내기 키·기기 이전·백업·잠금 상태별 접근은 iOS와 Android에서 각각 확인한다. 단순한 보안 저장소에 문자열을 넣는 것만으로 하드웨어 기반 개인 키 소유 증명이 구현됐다고 표현하지 않는다. PC의 비밀과 등록 상태는 OS 사용자 경계를 지키고 손상이나 권한 변경을 감지하면 안전하게 실패해야 한다.

페어링 완료 조건은 정상 등록 외에도 만료·재사용·중간자·잘못된 PC·취소 경쟁·재시작·철회 후 재접속·휴대폰 분실과 복구를 자동 및 실제 기기에서 검증하는 것이다. 초대 전달 경로와 연결 경로가 달라도 서로 같은 PC와 기기를 확인해야 한다.

**다음 설계 후보 — 미구현·미선정:** PC에서 확인한 정확한 Tailscale HTTPS origin과 단기 일회 등록 트랜잭션을 QR로 전달하고, 모바일이 그 origin의 TLS 인증서를 검증한 뒤 양쪽의 명시적 확인을 거치는 방안을 평가한다. 장기 bearer를 QR에 넣지 않는다. 정확한 origin의 인증서도 Snowball 프로세스 자체의 별도 신원을 입증하지 않으며, QR 복사·피싱과 근접성은 별도 검토가 필요하다. 현재 Expo SecureStore의 문자열 저장을 비내보내기 개인키로 간주하지 않는다. iOS Secure Enclave와 Android Keystore의 키 생성·서명·삭제를 네이티브 모듈에서 검토하며 지원 불가·소프트웨어 키·하드웨어 기반 키를 구분한다. [Apple Secure Enclave P-256](https://developer.apple.com/documentation/cryptokit/secureenclave/p256/signing) · [Android Keystore](https://developer.android.com/privacy-and-security/keystore) · [Expo SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/)

표준 인증 후보로 기기 승인 흐름과 요청별 키 소유 증명, 또는 FIDO/WebAuthn을 평가하되 아직 프로토콜이나 라이브러리를 확정하지 않았다. DPoP를 택하면 외부 origin·메서드·시간·nonce·재사용 검사의 신뢰 경계와 네이티브 비내보내기 키 서명 호환성을 구체적으로 검증해야 한다. 동기화 passkey는 자동으로 단일 기기의 비내보내기 키와 동일하지 않다. QR·기기 코드 자체가 피싱 방지를 보장하지 않는다. [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628) · [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449) · [RFC 10027](https://www.rfc-editor.org/rfc/rfc10027)

## 5. 네트워크 연결과 신뢰성

초기에는 PC와 클라이언트가 Tailscale 사설망에 있는 방식을 우선 검토한다. 실제 연결 시 각 OS의 Tailscale 설치·로그인, tailnet 정책과 인증서, Serve 지원 범위를 검증한다. 포트 공개·Funnel·라우터 포트 포워딩은 사용자에게 알리지 않고 활성화하지 않는다. 프록시는 원격 게이트웨이만 대상으로 하며 로컬 Supervisor에는 연결하지 않는다.

현재 브랜치의 읽기 전용 Tailscale 진단은 실행 파일을 명시적으로 선택받아 로컬 상태만 확인한다. 별도의 Serve 구성 스냅샷 해석기는 raw TCP와 TLS 종료·충돌·Funnel을 구분하지만 연결·PC 소유·실행 중인 백엔드를 증명하지 않는다. 개발용 게이트웨이는 직접 TLS 종료를 시험할 수 있으나 Tailscale 데몬과 게이트웨이가 같은 도메인 인증서를 사용할 수 있어 프록시가 TLS 종료 모드로 바뀌면 모바일의 일반 인증서 검증만으로 실제 게이트웨이를 구분하지 못한다. 게이트웨이 고유 신원 검증과 실제 기기 시험 전에는 연결 성공으로 표시하거나 자격을 전송하지 않는다. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) · [CLI 참고](https://tailscale.com/docs/reference/tailscale-cli)

앱은 최소한 PC 오프라인·절전·네트워크 전환·VPN 불가·인증 만료·권한 철회·일시적 연결 실패를 구분하고, 마지막으로 실제 확인한 시각과 재시도 방법을 표시한다. 모바일 백그라운드 연결은 보장하지 않는다. 복귀 시 새 인증으로 스냅샷을 다시 읽고, 실시간 이벤트의 누락 또는 서버 재시작 시 재동기화한다. 푸시는 민감 내용을 담지 않는 알림 또는 동기화 힌트로 다루고, 실패해도 수동 조회를 막지 않는다.

접수와 실행 완료를 구분한다. 명령은 대상·권한·고유 ID에 묶고 연결 단절 또는 타임아웃 후 결과를 조회한다. 결과가 불확실하면 불확실하다고 표시하며, 새 ID로 자동 재전송하거나 다른 세션에 보내지 않는다. 승인·중단과 세션 생성도 동일하게 원래 대상과 실제 하네스 결과에 결부한다.

대중 배포 전 직접 경로와 중계 경로, 여러 통신사·사설망·방화벽·절전·재부팅·PC와 모바일의 네트워크 변경을 실측한다. 지연·실패율·복구 시간 목표와 측정 방법을 출시 전에 정하고, 장애 시 알림·지원·복구 절차와 서버 의존 범위를 공개한다. 네트워크가 항상 무오류라고 약속하지 않는다. 향후 전용 중계를 도입한다면 데이터가 중계자에게 보이는 범위, 운영 비용·가용성·남용 방지 및 장애 시 로컬 독립성을 별도 검증한다.

## 6. 원격 API와 모바일 제품 범위

- API는 버전·호환성·요청 및 응답 크기·권한을 명시한다. 연결된 기기가 볼 수 있는 데이터의 범위를 응답에도 적용하며 스냅샷 전체를 반환하지 않는다.
- 단계적으로 PC 상태, 허용된 하네스·프로젝트·세션, 대화와 작업 상태, 명시적 메시지 전송·중단·승인을 제공한다. 각 기능의 실제 하네스 지원 여부를 동적으로 표시한다.
- 사용자는 연결·조회 중·정보가 오래됨·권한 없음·완료·결과 미확인을 구분할 수 있어야 한다. 화면 잠금·백그라운드·알림·기기 분실 시 민감한 데이터 노출을 줄인다.
- 외부 웹은 인증된 별도 UI와 브라우저 전용 보호를 갖춘 후에 제공한다. 네이티브 앱용 bearer 인터페이스를 그대로 웹에 공개하지 않는다.
- 스토어 출시 전 실제 iOS/Android의 TLS·리다이렉트·키 저장·앱 수명 주기, OS 버전과 접근성, 다국어 및 계정 삭제·개인정보 고지를 검증한다. Metro 번들 또는 시뮬레이터 성공만으로 실기기 연결을 보장하지 않는다.

## 7. 설치·업데이트와 공급망

1. OS·CPU별 PC 배포물을 만들고, 사용자에게 지원 OS와 사전 요구사항을 명시한다. npm 경로는 Node가 이미 있는 사용자의 선택지이며 npm 패키지명과 배포는 확보·게시 후에만 안내한다.
2. 모든 구성 저장소와 의존성 버전을 릴리스 manifest에 고정한다. 실행 시 여러 저장소의 움직이는 `main`을 각각 합친 결과를 단일 검증 릴리스로 표현하지 않는다. manifest 자체는 서명과 출처 확인이 필요하다.
3. Windows 서명, macOS 서명·공증과 플랫폼별 무결성 검증을 적용하고, 키 관리·폐기·교체·릴리스 권한 및 의존성 취약점 대응을 정의한다. 단순 다운로드 체크섬만으로 발행자 신원을 증명하지 않는다.
4. 업데이트는 별도 위치에 준비하고 서명·호환성·상태 마이그레이션을 검증한 후 전환한다. 중단·디스크 부족·시작 실패 때 이전 작동 버전과 사용자 설정·자격을 복구한다. 다운그레이드와 만료된 메타데이터의 악용도 고려한다.
5. 기존 설치의 경로와 자동 시작 선택, 기기 등록, API 설정과 데이터를 보존하고 안전하게 이전한다. 임의의 실험 브랜치에 `main`을 혼합하지 않는다. PC 업데이트와 펌웨어 업데이트는 분리하며 기기 업데이트의 명시적 선택과 전체 백업 절차를 유지한다.
6. Windows·macOS·Linux 실제 환경에서 최초 설치, 갱신, 중간 실패와 복구, 제거 및 재설치를 검증한다. 현재 `snowball update`는 기존 소스 설치 경로의 단축일 뿐 위 요구사항을 충족한 배포 시스템이 아니다.

## 8. 멀티 저장소 작업과 호환성

작업 브랜치는 Control, Middleware, Device_M5Stack 및 독립 하네스 세 저장소에 같은 이름으로 유지할 수 있지만, 이름 일치만으로 해당 버전이 함께 설치되는 것은 아니다. 기존 설치기는 `main`을 가져오므로 실험 조합에 사용하기 전에 설치 경로를 격리하고 정확한 커밋을 확인한다. Control의 `scripts/workspace-revisions.mjs`는 깨끗한 Git 체크아웃의 브랜치와 SHA를 기록·확인하는 개발 도구이며, 무시된 파일·외부 의존성까지 고정한 서명 릴리스는 아니다.

변경되는 계약별로 Middleware·Control, 웹·MK20·M5Stack, Codex·Antigravity·OpenCode 및 SDK/worker에 미치는 영향을 검토한다. 펌웨어 변경 없이 가능한 기능은 하드웨어에 억지로 전파하지 않는다. 의존 저장소를 먼저 반영하고 통합 대상 SHA를 기록하며, 저장소별 CI와 별도로 실제 조합을 검증한다. 하네스의 SDK 묶음이나 프로토콜 변경 시 관련 저장소의 버전·호환성과 독립 테스트를 함께 갱신한다.

## 9. 단계별 완료 조건

| 단계 | 산출물 | 완료 조건 |
| --- | --- | --- |
| 0. 기반 | 격리된 개발 브랜치, 제한된 게이트웨이·앱 실험, 개발 조합 점검 | 로컬 회귀 및 경계 테스트가 통과하고 미지원 기능을 명시한다. 이 단계는 원격 출시가 아니다. |
| 1. PC와 기기 신뢰 | 로컬 활성화·등록·목록·철회, 검토된 페어링과 저장소 | 인증·권한·도난·복구·변조 시험 및 실제 양쪽 기기 검증을 통과한다. |
| 2. 사설 원격 연결 | 인증된 게이트웨이와 Tailscale 기반 네이티브 접속 | 서로 다른 네트워크의 실제 기기에서 정상·단절·절전·철회·재동기화를 검증한다. 미인증 Supervisor는 노출되지 않는다. |
| 3. 외부 웹과 모바일 | 버전된 제한 API, 원격 웹 및 모바일 핵심 작업 | 읽기·전송·중단·승인의 권한과 실패 상태를 검증하고 각 하네스 지원 범위를 표시한다. |
| 4. 배포와 사용자 신뢰 | 서명된 설치·안전한 업데이트, 문서·지원·사고 대응 | 플랫폼별 최초 설치·업그레이드·복구와 독립 보안 검토를 통과하고 측정된 한계를 공개한다. |
| 5. 대중화 검토 | 필요 시 전용 중계 및 온보딩 개선 | 실제 수요, 비용·운영·보안·가용성 평가를 마치고 로컬 독립성을 검증한다. |

단계는 의존성과 검증 순서를 나타낸다. 동시에 작업할 수 있지만 앞 단계의 보안 완료 조건을 생략해 공개하지 않는다.

## 10. 검증 및 출시 기록

자동 검사는 원격 거부·인가·철회·정보 필터링·제한·재생·동시성·저장소 손상·네트워크 단절·명령 중복·업데이트 복구를 포함한다. 기존 로컬 회귀와 실제 Web/MK20/M5Stack·하네스 영향 검증을 병행하고 해당되지 않는 항목도 근거를 기록한다. 보안 테스트는 단위 테스트 외에 독립 리뷰 및 침투 검증을 포함한다.

각 인도 시 변경 커밋과 사용한 6개 저장소 SHA, 빌드·테스트 환경, 통과·실패·생략, 실제 기기와 네트워크 검증 여부, 알려진 취약점 및 지원 한계를 남긴다. 기존 테스트 결과를 현재 변경과 다른 커밋이나 하드웨어의 인수 결과로 사용하지 않는다.

**격리 설치 검증:** Linux에서 Control `0561775`, Middleware `2b4c610`, M5Stack `13c8bf2`, Antigravity `a73997b`, Codex `121f490`, OpenCode `b5e577d`를 공식 저장소에서 새 임시 경로에 고정 checkout했다. Web 프로필과 세 하네스를 빌드하고 하네스 entry digest를 확인한 뒤, 별도 임시 상태 디렉터리로 실제 suite를 시작해 루프백 snapshot 응답과 정상 종료를 확인했다. 기존 PATH·설치 폴더는 변경하지 않았고, 네이티브 하네스 명령이나 기기 쓰기는 수행하지 않았다. 이 검증은 실제 Tailscale 연결, 모바일 실기기, 그래픽 트레이 또는 서명 배포 검증이 아니다. 같은 Middleware 변경의 자동 검사는 349개 통과·11개 생략, 모바일 검사는 14개 통과했다. 실제 Antigravity 세션을 요구하는 전환 스크립트는 이 환경에 해당 세션이 없어 실패했다.

**한 줄 실행기 검증:** Middleware `f712fb1`의 Linux 자동 검사는 352개 통과·11개 생략했다. 실제 GitHub 브랜치를 `npx --ignore-scripts`로 받아 도움말이 표시되고 설치·`--update` 옵션이 기존 설치기에 전달되는 것을 잘못된 프로필의 조기 거부로 확인했다. 이 검사에서는 기존 폴더를 만들거나 갱신하지 않았다. 이후 Windows에서 새 고정 설치 모드로 제공된 여섯 기준 SHA를 격리 경로에 실제 설치하고 별도 상태의 Web 루프백 snapshot을 확인했다. npm 패키지 실행기 경유와 PowerShell 5 manifest 인코딩은 자동 검사했다. WSL Ubuntu에서는 집중 검사 29개와 여섯 기준 SHA의 실제 체크아웃 검증을 통과했다. 실행기는 서명되지 않았으며 Linux 데스크톱 전체 설치, Windows 일반 업데이트와 macOS 실물 설치·업데이트는 이 검사로 인증하지 않는다.

**Windows 후속 회귀:** Middleware `4b8e9a1` 전체 검사 350개 통과·20개 생략, MK20 parity 10개 통과·1개 생략, Control 호스트 70개 통과·2개 생략, MK20 플러그인 17개·M5Stack 23개·하네스 7/2/9개 통과. 실제 하네스 전환은 프롬프트 전송 없이 통과했다. 승인된 MK20 ADB 연결이 없었고, Tailscale 설치가 완료되지 않아 실물 화면과 Serve·휴대폰 연결은 미확인이다.
